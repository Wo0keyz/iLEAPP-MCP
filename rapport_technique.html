iLEAPP-MCP

Rapport Technique, Sécurité & Architecture Intégrale

Serveur Model Context Protocol pour l'Automatisation Forensique iOS

1. Introduction et Contexte

Le projet iLEAPP-MCP vise à combler le fossé entre l'intelligence artificielle (les LLMs) et l'analyse numérique légale (Digital Forensics) de systèmes iOS. L'outil iLEAPP (iOS Logs, Events, And Plists Parser) génère des extractions riches et complexes (Bases SQLite, fichiers TSV). Fournir ces gigaoctets de données brutes directement à une IA est techniquement impossible en raison des limitations de la fenêtre de contexte (Token limits).

La solution réside dans le Model Context Protocol (MCP), un standard open-source. Le serveur MCP agit comme une API locale sécurisée qui expose des "Outils" (Tools) au modèle d'IA. Ainsi, l'IA n'ingère plus la donnée en masse, mais interroge dynamiquement le système d'investigation en fonction de son raisonnement.

2. Architecture Interne du Serveur

Le serveur est architecturé autour de trois piliers principaux garantissant performance et découplage :

2.1. Le gestionnaire FastMCP (server.py)

Il assure la communication JSON-RPC via les flux standard (stdio) ou SSE avec l'environnement client (Claude Desktop, Cursor). Il se contente d'enregistrer les fonctions décorées par @mcp.tool() et ne contient aucune logique métier d'analyse.

2.2. Le Cœur du Réacteur : CaseManager (case.py)

C'est la classe Singleton qui gère l'état et l'accès aux extractions :

  • Indexation intelligente : À l'appel de load_case(), il détecte automatiquement la racine du rapport iLEAPP et indexe récursivement les fichiers pertinents dans des dictionnaires mémoires (Optimisation LFI et Path Traversal).
  • Pool de connexions : Il maintient un cache thread-safe des connexions SQLite.
  • Estimateur de Pagination : Il intercepte les requêtes SQL, calcule le COUNT(*) pour l'IA, et injecte automatiquement les clauses LIMIT et OFFSET.
  • Parseur TSV Multi-encodage : Résilience de lecture des CSV/TSV via un essai successif d'encodages (utf-8-sig, utf-8, latin-1, cp1252).

2.3. Les Modules Métiers (modules/)

Chaque domaine forensique dispose de son module spécialisé, interrogeant le CaseManager et renvoyant des objets Pydantic fortement typés :

  • messages.py : Agrégation unifiée SMS, iMessage, WhatsApp, Telegram, Signal.
  • locations.py : Analyse des positions, Significant Locations, Routine cache.
  • timeline.py : Génération d'une frise chronologique unifiée multi-sources.
  • apps.py & web.py : Applications installées, permissions et navigation Safari/Chrome.

3. Sécurité & Intégrité Forensique

Dans un contexte pénal ou d'incident response, la règle d'or est l'immuabilité de la preuve. Un LLM, sujet aux hallucinations ou aux prompt injections, ne doit jamais pouvoir altérer l'extraction.

3.1. Sécurité des Bases de Données (Anti-Mutation)

Défense en profondeur (Defense-in-depth) :
  1. Moteur SQLite (C Level) : Toutes les connexions sont initiées via URI avec l'argument ?mode=ro. Il s'agit d'une protection au niveau du système de fichiers virtuel SQLite : l'écriture est physiquement rejetée.
  2. Filtre Lexical Regex : L'outil d'exécution SQL libre (run_readonly_sql) impose une liste blanche de verbes (SELECT, WITH) et rejette fermement les multiples requêtes et mots clés comme DROP, UPDATE, ou PRAGMA WRITABLE_SCHEMA.
  3. Assainissement dynamique : Les noms de tables fournis par l'IA sont purgés des backticks et quotes pour éviter les évasions syntaxiques (SQLi).

3.2. Protection Anti-Déni de Service (DoS) et Mémoire

  • Explosion de contexte LLM : Les limites (limit) envoyées par l'IA sont écrêtées par le serveur (ex: max 250). Une réponse massive paralyserait l'API du modèle d'IA. Le serveur renvoie toujours un objet paginé avec les métadonnées has_more et total_count.
  • DoS par indexation (LFI) : Si une IA malveillante demandait d'indexer la racine du système (C:\), la recherche récursive rglob("*") saturerait la mémoire. Le CaseManager est verrouillé par un compteur coupe-circuit (max 50 000 fichiers scannés).

4. Innovations Algorithmiques Métiers

4.1. Normalisation Tolérante aux Fautes : _find_field

iLEAPP est composé de centaines de plugins communautaires. La convention de nommage des colonnes n'existe pas (ex: "Message Date", "message_date", "Date"). La fonction _find_field effectue un matching insensible à la casse et aux séparateurs (espaces, underscores, tirets) pour extraire la donnée indépendamment du parseur sous-jacent.

4.2. Moteur Géospatial Local (Haversine)

SQLite natif ne dispose pas de capacités géospatiales sans l'extension compilée SpatiaLite. Pour permettre à l'IA de faire des requêtes du type "Qui était dans un rayon de 5km de ces coordonnées ?", la formule mathématique de Haversine a été implémentée en Python pur dans locations.py. Les coordonnées sont filtrées en mémoire post-requête SQL de manière transparente.

5. Installation et Configuration

5.1. Déploiement Local

# Cloner le dépôt et se placer à la racine
git clone https://github.com/Wo0keyz/iLEAPP-MCP.git
cd iLEAPP-MCP

# Installer le package et ses dépendances (Python 3.10+)
pip install .

L'installation rend la commande système ileapp-mcp disponible globalement.

5.2. Connexion à Claude Desktop / Cursor

Éditez le fichier de configuration de votre client IA (ex: claude_desktop_config.json) pour déclarer le serveur MCP :

{
  "mcpServers": {
    "ileapp-mcp": {
      "command": "ileapp-mcp",
      "args": []
    }
  }
}

6. Utilisation & Personas d'Investigation (Agents)

Pour exploiter toute la puissance du serveur, des fichiers de configuration système (System Prompts) sont fournis dans le dossier agents/ du projet.

  • analyste_forensic.md : Configure le modèle pour agir comme un technicien strict, croisant la timeline, justifiant chaque allégation par l'horodatage et la source exacte sans hallucination.
  • profileur_comportemental.md : Demande au modèle d'utiliser des algorithmes de reconnaissance de patterns (trous de sommeil, géolocalisations nocturnes récurrentes pour le domicile, pics de messagerie tardifs pour l'Inner Circle social).
Exemple d'amorce opérationnelle :
"J'ai configuré tes accès MCP. Charge le dossier situé à C:\CTF_GrayKey. Suis ta SOP d'analyste et sors-moi une timeline des événements 2h avant et après la dernière position connue de l'appareil."

7. Conclusion & Limites

Le serveur iLEAPP-MCP révolutionne la phase de triage et d'analyse comportementale d'une extraction iOS. En bridant structurellement et conceptuellement le LLM via un protocole d'outils stricts et paginés, le risque d'hallucination disparait au profit d'une requête analytique extrêmement rapide et documentée.

Limites connues (Angles Morts) :

  • Analyse Visuelle (Computer Vision) : Le texte ne peut analyser les snapshots de l'interface utilisateur (Fichiers .ktx de cache d'applications).
  • Dépendance iLEAPP : Le serveur ne peut requêter que ce que les plugins iLEAPP ont parsé. L'exploitation d'artefacts très obscurs ou non supportés nécessite encore le recours au Full File System brut ou à une suite propriétaire complète (ex: Magnet Axiom, Cellebrite Physical Analyzer).
